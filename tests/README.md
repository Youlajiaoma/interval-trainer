# Tonaloom 本地测试

从项目根目录运行。基础检查只使用 Node 自带工具，不需要安装 npm 依赖；本次在 Node 24.12.0 上验证。

## 一个入口

```powershell
node tests/run.cjs
```

命令会运行基础功能和回归检查，并在所需文件已存在时运行离线缓存模拟。输出明确区分“通过”“失败”“跳过”。有功能失败时，命令返回非零退出码，不能用于宣称检查全部通过。

```powershell
node tests/run.cjs --details
node tests/run.cjs --full
node tests/run.cjs --help
```

- `--details`：补充失败断言的详细原因。
- `--full`：还要求三项真实浏览器检查。任何检查失败或因缺少条件而跳过，均返回失败。
- 不带 `--full` 时，不启动浏览器；三项浏览器检查仍会列为跳过，不会省略它们。

基础脚本按 `tests/test_*.cjs` 自动发现；`test_sw.cjs` 和 `test_staff_interval.cjs` 按额外条件处理。Python 浏览器脚本由完整检查明确调用。

需要单独排查某项时，可以直接使用 Node 自带测试入口，例如：

```powershell
node --test --test-reporter=spec tests/test_flows.cjs
node --test --test-reporter=spec tests/test_regressions.cjs
```

## 阶段 0 的结果基线

2026-10-15，本阶段没有修改 `site/` 中的功能代码，也没有修复审查发现的问题。默认命令实测结果为：**16 项通过、12 项失败、4 项跳过，退出码为 1**。

十二项失败对应审查中的九类问题，A7 分成四种情况。它们断言的是应当实现的正确行为，没有使用“预期失败”或反向断言来算作通过。后续修复时应让功能达到预期，再由这些检查确认；不要仅为得到通过结果而放宽断言。

| 编号 | 检查的正确行为 |
|---|---|
| A1 | 音符统计页清空历史只清除音符记录，其他模块不变 |
| A2 | 导出再恢复后，两个谱号的高编号记录、日统计和复习进度完整保留 |
| A3 | 备份最后一部分无效时，不覆盖任何已保存数据 |
| A4 | 按当前保留数量生成的完整备份，可以从文件入口重新导入 |
| A5 | 两个窗口各答一题后，重新打开仍保留两题 |
| A6 | 同一小节 C♯4、D4、C4 中，第三个音带必要的还原号 |
| A7 | 答对／显示答案后立即返回再进入／刷新，均能继续且不重复计分 |
| A8 | 音符首次答错后刷新，重答不能把它变成首次答对 |
| A9 | 仅选择纯一度的旧设置不会让旋律练习陷入无法进入的状态 |

旧设置检查记录当前仍支持的行为。后续若明确调整记录格式或旧格式支持范围，应同步说明新的约定，再调整对应测试。

## 覆盖范围与隔离方式

- `test_review.cjs`：已有的复习安排、昨日错题、每日统计、历史备份等检查。
- `test_indexeddb.cjs`：已有的保存、重读及旧记录读取检查，使用内存模拟数据库。
- `test_logic.cjs`：独立核对 793 组音高及音名字母间距、出题音区、旋律方向统计。
- `test_resources.cjs`：核对 61 个钢琴采样键、96 个旋律录音组合和文件基本完整性。
- `test_flows.cjs`：四模块导航、正常答题保存和重复点击防护等正常流程。
- `test_regressions.cjs`：上表中的失败场景。

新增流程检查直接载入现有的应用、复习、统计和存储脚本，不复制备份或答题实现。只替代必要的外部环境：页面元素、时钟、IndexedDB、音频设备及记谱组件。

每个检查默认建立独立内存数据库；刷新和多窗口用例只在该用例内共享它。延时反馈使用可推进的测试时钟，不必实际等待。不会打开日常浏览器、读取用户练习数据或访问外部网络。

**这些模拟检查不能证明界面和声音正确。** 还原号检查验证程序向记谱组件传入的符号；没有运行真正的 VexFlow。音频文件检查不验证实际音高，模拟播放也不会发声。符干、排版、溢出、真实音频和 Service Worker 行为仍需要浏览器及人工检查。

## 额外资源与浏览器条件

离线缓存模拟需要 `site/vendor/vexflow.js`。正式发布流程会下载固定版本 VexFlow 5.0.0，本地仓库没有附带该文件；运行器不会下载、伪造或生成它。缺少文件时明确跳过，完整检查会因此返回失败。

浏览器检查另外需要：

| 脚本 | 额外条件 |
|---|---|
| `test_staff_interval.cjs` | Node 版 Playwright、Chromium、本地 VexFlow 文件 |
| `test_ui_embedded.py` | Python、Python 版 Playwright、Chromium |
| `test_pwa_integration.py` | Python、Python 版 Playwright、Chromium、本地 VexFlow 文件、本地网页服务 |

这些依赖当前没有安装，本阶段也未安装。Node 版和 Python 版 Playwright 不能相互替代；准备安装或下载应另行安排，不由运行器自动执行。

已准备好上述条件后，在另一个终端启动本地网站：

```powershell
python -m http.server 8000 --directory site
```

随后运行 `node tests/run.cjs --full`。运行器只接受本机 HTTP 地址作为 PWA 测试目标，不会启动网页服务或使用线上站点。

- `CHROMIUM_PATH`：可指定已安装的 Chromium／Chrome 可执行文件。
- `PYTHON`：可指定运行器使用的 Python 可执行文件。
- `PWA_TEST_URL`：可改用其他本机端口，默认 `http://localhost:8000/`。

浏览器脚本创建独立的临时浏览器环境，不使用日常浏览器资料。界面脚本会在系统临时目录保存截图；PWA 脚本会在隔离环境中写入测试记录、离线缓存并测试备份下载。这些不会进入项目的真实练习数据，但属于临时文件和浏览器环境写入，不能称为纯只读检查。

## 后续检查原则

每个修复阶段先运行相关检查，再运行统一入口。发布前应补齐完整检查的条件，并完成实际手机、电脑和声音验收。基础检查通过、浏览器检查通过、用户验收通过需要分别说明。

当前运行器没有接入 GitHub Actions；本阶段未改动发布配置，也不会创建提交或触发部署。
